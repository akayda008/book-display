## 2026-09-03 — Single/two-page preference reached `pagesPerView` but not the actual rendered layout

**What happened:** Sub-project 5's single/two-page toggle was wired into `pagesPerView` (`isMobile || singlePage ? 1 : 2`), which controls how many pages are generated/advanced per click. But the actual visual decisions - which of the two page columns is `hidden`, which page-turn animation flavor plays (two-page spine-flip vs. single-page 360deg spin), the spine-side gutter, and the turning leaf's positioning - were all still keyed directly on the raw `isMobile` viewport flag throughout the render section, not on anything that accounted for the `singlePage` preference. So on a desktop-width window with "Single page" checked, `pagesPerView` correctly dropped to 1 (which is why the leading blank page disappeared - the blank-page insertion logic reacts to `pagesPerView`), but the left page column stayed visible and the reader still visually looked like a two-page spread.

**Why it happened:** `pagesPerView`'s definition was updated to fold in the new preference, but the render section's several *other*, separate `isMobile` checks - written before this milestone, when `isMobile` and "should show one page" were the same thing - weren't re-audited for the same change. Updating the one formula that happened to be phrased as a computed variable gave a false sense that the preference was fully wired in, without tracing forward to everywhere else "is this a one-page or two-page layout" gets decided independently in the same file.

**Impact:** Reported by the user in the first manual-verification round for Sub-project 5 (`feature/reading-preferences`, never merged to `develop`) - the single-page checkbox appeared to do nothing except remove the leading blank page. Fixed by introducing one derived `singlePageView = isMobile || singlePage` and routing every single/two-page-shaped decision through it instead of `isMobile` directly (column visibility, animation flavor/`isSinglePagePrevious`, leaf-face sides, gutter, leaf positioning, and the measurement clone's structure, which must stay identical to the real page per the pagination-measurement-mismatch mistake below). The one deliberate exception is the frame's aspect-ratio/sizing (`frameSizeStyle`), which Design Direction fixes to the true viewport width regardless of the single-page preference, and was left on `isMobile`.

## 2026-09-02 — Chapter-reporting effect read the wrong page of the two on-screen, delaying/misreporting the URL at a chapter boundary

**What happened:** The chapter-reporting effect in `Book.tsx` (the one that tells `ChapterReader` which chapter to put in the URL) preferred `leftPage` (`pages[currentPage]`), only falling back to `rightPage` when `leftPage` wasn't a text page. That's backwards on both platforms. On mobile, only `rightPage` is ever actually rendered to the reader (`baseRightPage` - the flip code's own comment on the leaf-front page during a mobile turn says so outright: "the single page currently on screen"); `leftPage` there is what was just flipped away from, one step behind. On desktop, `rightPage` is the further-along, right-hand page of the two-page spread. Net effect: on mobile, the URL only updated one flip *after* actually landing on a new chapter's first page (reporting the page before, not the page shown). On desktop, a spread that straddled a chapter boundary (chapter A's last page on the left, chapter B's first page on the right) kept the URL on chapter A even though chapter B's content was already visible on the right.

**Why it happened:** The bug-fix round that introduced this effect (see the `router.replace()`/`history.replaceState` entry above) was scoped to the navigation-mechanism bug and didn't separately re-derive which of `leftPage`/`rightPage` is actually "what the reader is looking at" on each platform - it reused `leftPage` first by default (the more natural-sounding "primary" page), without checking it against the flip-rendering code's own established convention a few dozen lines further down in the same file.

**Impact:** Reported by the user in the same manual-verification pass as the bounce-loop bug, on the corrected build - a URL-accuracy issue, not a broken/stuck reader (the earlier bounce-loop fix already made forward/backward flipping itself work correctly). Fixed by flipping the priority: prefer `rightPage`'s chapter, falling back to `leftPage` only when `rightPage` isn't a text page (the book's last page on an odd-length desktop spread, or past the end of the book) - a single, non-platform-conditional change that corrects both the desktop and mobile symptoms at once.

## 2026-09-02 — URL-tracking `router.replace()` re-triggered the reader's deep-link buffering on every chapter crossing, causing an infinite bounce

**What happened:** Sub-project 4's chapter-URL-tracking feature (`ChapterReader.tsx`) called `next/navigation`'s `router.replace()` whenever the reader flipped into a new chapter, to keep the address bar honest. That's a real Next.js App Router navigation, not just a URL change: it re-renders `app/[bookSlug]/[chapterSlug]/page.tsx` (a Server Component) for the new `chapterSlug`, which hands `Book` a *new* `initialChapterId` prop value. `Book`'s deep-link-buffering effect (meant to run once, on the initial page load of a chapter deep-link) has `initialChapterId` in its dependency array, so the changed prop re-ran it on every chapter crossing too - wiping the in-memory `pages` array and resetting `currentPage` to a freshly recalculated position. That recalculated position lands on the nearest `pagesPerView` boundary (a known, pre-existing limitation - see Architecture.md), which for an unlucky page-count parity landed back on the *previous* chapter's last page instead of the new chapter's first. `Book`'s chapter-reporting effect then saw the previous chapter's id again and fired `onChapterChange` with it, so `ChapterReader` called `router.replace()` back to the previous chapter's URL - flipping the reader back and forth between the two chapters on every further click, with no way to progress.

**Why it happened:** `router.replace()` reads, in the App Router, as "just update the URL, no navigation" (the natural intent for a shallow URL sync) but it isn't - it's the same navigation machinery as `router.push()` minus the history entry, still re-rendering the route's Server Component and everything under it. The interaction with `Book`'s deep-link-buffering effect (a mechanism built for a different purpose - the *initial* page load of a deep link, not routine in-page flipping) wasn't traced through before shipping, even though the effect's own dependency array made the re-trigger visible on inspection.

**Impact:** Reported by the user as flipping forward getting stuck right at a chapter boundary - Next would snap back to the previous chapter and further clicks bounced between the two chapters instead of progressing through the book. Caught after Sub-project 4 merged to `develop` (real regression, not caught pre-merge since this class of bug only shows up when actually clicking through a live chapter boundary, not from static code review). Fixed on `bug/chapter-url-replace-navigation` by switching `ChapterReader` to the raw History API (`window.history.replaceState`) instead of `router.replace()` - it updates only the address bar, with no React re-render and no Server Component re-run, so `Book`'s `initialChapterId` prop never changes after the initial mount and the buffering effect no longer re-triggers.

## 2026-09-02 — Shelf-opening transition animated layout properties instead of transform/opacity

**What happened:** The Sub-project 4 shelf-to-reader Motion transition (the growing-rectangle cover/reveal) animated the overlay element's `x`/`y`/`width`/`height` directly. Motion resolves those specific prop names to real CSS `top`/`left`/`width`/`height` styles, not a `transform` - so every animation frame forced the browser to recompute layout for that element, instead of compositing a GPU-cheap transform. Reported by the user as the transition looking choppy.

**Why it happened:** The overlay was built by literally growing a box from the clicked card's measured rect to the viewport rect, which reads naturally as "animate its size and position" - the most direct-sounding implementation, but the wrong one for this project's own Engineering Principle 2 (animate only cheap `transform`/`opacity` properties, the same rule the page-turn animation already follows). The choice wasn't re-checked against that principle before shipping, even though it's stated in the project's own docs and demonstrated elsewhere in the codebase (`Book.tsx`'s flip only ever animates `rotateY`).

**Impact:** Reported in the first manual-verification round after Sub-project 4 landed on its feature branch (never merged to `develop`). No functional breakage - the transition still played, just not smoothly. Fixed by keeping the overlay element always at `fixed inset-0` (full viewport, never resized) and instead animating a `translate(...) scale(...)` transform computed to make it visually match the origin/target rect, moving toward/away from the identity transform.

## 2026-09-02 — Round 1's image-centering fix patched a symptom, not the underlying breakpoint mismatch

**What happened:** The single-page image-centering bug (reported in Sub-project 3 verification round 1) was fixed by having only `image`-kind pages cancel out the spine-side gutter padding with a counter-margin. That made the *reported* case (an off-center image between 768-1024px) go away, but the actual defect was one layer down: the gutter padding, several padding/text-size tiers, and the frame's outer spacing were all still keyed to Tailwind's default breakpoints (`md:` at 768px, `lg:` at 1024px), left over from before Sub-project 2 moved the reader's own single/two-page cutoff to a JS-driven 1200px. That mismatch affected *any* content in the single-page view, including text pages - which round 1's image-only fix didn't touch, so the same misalignment was still present on text pages and wasn't caught until the user re-checked more broadly in round 2.

**Why it happened:** The investigation for round 1 correctly identified *a* breakpoint mismatch causing the reported symptom, but stopped at the smallest change that made that one symptom disappear (scoping the fix to `image`-kind pages, since that was the only content type mentioned in the report) rather than asking why a CSS-breakpoint-driven style existed at all inside a range now governed by a different, JS-driven breakpoint. The narrower fix was verified against the literal repro (an image page at a specific width) rather than against the general question "does anything else in this component still branch on 768px/1024px inside the 0-1200px single-page range."

**Impact:** Cost one extra verification round. No user-facing harm beyond the bug persisting for text pages (which was already present before this milestone, just not previously noticed) and one wasted, superseded code change (the `image`-only counter-margin), which round 2 replaced with a fix at the actual source (making the gutter, padding, text size, and gap spacing depend on the JS `isMobile` flag rather than Tailwind's default breakpoints, for both text and image pages alike).

## 2026-09-02 — Desktop Previous flip landed the wrong page's content on the leaf's back face

**What happened:** The desktop spine-flip's "leaf" element has a front face (what's showing before the turn) and a back face (what should be showing once the turn lands). For the Previous direction, the leaf pivots at its right edge and rotates so it ends up lying over the *right* page slot (mirrored across the spine, the same way Next's leaf ends up over the *left* slot). The back face's content should therefore be the page that's about to become the new *right* page. Instead, the code computed it as `pages[currentPage - pagesPerView]` — the page about to become the new *left* page (the same index used, correctly, for what the base layer reveals underneath on the left). Both faces referenced the same, wrong index. Visually this meant the leaf settled showing the wrong content on the right for an instant, until the state update at the end of the animation replaced it with the correct page — a visible content pop right as the turn completed.

**Why it happened:** The formula for "what the leaf's back face shows" was written by copying the pattern used for "what the base layer reveals on the *left*" (`pages[currentPage - pagesPerView]`), without separately re-deriving where the leaf itself physically lands (the *right* slot, one page index later: `pages[currentPage - pagesPerView + 1]`). The Next direction's equivalent formula happened to be correct because there, the leaf's landing slot (left) and the "revealed" slot needing that same left-hand new content are the same index — so the shortcut worked by coincidence in one direction and not the other, and wasn't re-verified for the second direction on its own terms.

**Impact:** Reported by the user as the two-page spread looking like it was "skipping" content when clicking Previous, alongside a since-corrected overreaction (round 1) that changed the advance step entirely instead of finding this bug. Caught during round 2 of manual verification, never merged to `develop`. Fixed by deriving the back face's index correctly (`currentPage - pagesPerView + 1`, the new *right* page) instead of reusing the base-reveal formula.

## 2026-09-02 — Off-by-one buffer guard could show a blank page after a flip

**What happened:** The initial page-turn implementation guarded against flipping into a page that hadn't been generated yet, but the guard's arithmetic checked the wrong index. It verified that `pages[currentPage + pagesPerView - 1]` existed, when the page actually needed after the click was `pages[currentPage + pagesPerView]` — one further ahead. On mobile in particular (`pagesPerView` was 1 at the time), that condition was true trivially on every click regardless of whether the target page had actually been buffered, so the guard never meaningfully blocked anything. The mobile mid-flip content swap could then land on an unbuffered index, rendering the fallback empty page.

**Why it happened:** The guard was written by reasoning about "does the buffer cover the click" in terms of array length versus the *pre-advance* current page, without explicitly working out which index would actually be read *after* the state update. It happened to be harmless on desktop at the time only because desktop's larger `pagesPerView` and generous buffer target usually papered over the gap in practice, not because the formula was correct there either.

**Impact:** Reported by the user as "blank page after the mobile flip animation completes." Caught during the milestone's manual-verification pass (never merged to `develop`), fixed by correcting the guard to check `currentPage + ADVANCE_STEP` (the actual post-advance index) and, more fundamentally, by removing the mid-animation content swap entirely in favor of a front/back leaf-face trick that only updates React state once the animation fully completes — eliminating the class of bug, not just the one instance.
